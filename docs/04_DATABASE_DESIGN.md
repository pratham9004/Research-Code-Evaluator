# Database Design

## 1. Purpose

The database stores the research data generated by every AI-versus-human code comparison.

The database is the persistent research dataset.

Raw measurements and calculated results must both be retained.

## 2. Comparison

One completed comparison represents:

- One predefined problem
- One programming language (Python, Java, C++, or JavaScript)
- One AI-written code
- One human-written code
- Their execution results
- Their analysis results
- Their comparison results

Each comparison receives an automatically generated unique internal ID.

## 3. Comparison Fields

A comparison record contains:

- comparison_id
- problem_id
- language (one of: python, java, cpp, javascript)
- AI name
- AI source code
- human source code
- status
- created_at
- completed_at

No participant ID is required.

## 4. Problem

Each problem contains:

- problem_id
- title
- description
- category
- difficulty
- supported languages (a list; may include python, java, cpp, javascript)
- version

Problems belong to the predefined research problem bank.

## 5. Test Cases

Each problem contains predefined test cases.

Each test case contains:

- test_case_id
- problem_id
- input
- expected output
- case type
- version

The same test cases are used for both AI and human code regardless of language.

## 6. AI Data

For every comparison, store:

- AI name
- AI source code

The AI name may be:

- ChatGPT
- Claude
- Gemini
- Other AI system

The software does not store AI API credentials.

## 7. Human Data

For every comparison, store:

- Human source code

No human name is required.

No participant ID is required.

## 8. Execution Results

For each code variant, store:

- Total test cases
- Passed count
- Failed count
- Error count
- Timeout count
- Pass rate
- Execution time (runtime only; compilation time stored separately if applicable)
- Execution status
- Individual test-case results

Each result must identify whether it belongs to:

- AI
- HUMAN

### Compilation Results (C++ and Java)

For compiled languages (Java, C++), also store:

- Compilation status (SUCCESS / FAILED)
- Compilation time in milliseconds
- Compilation error output (if applicable)

Compilation failure is stored as execution_status = ERROR with a descriptive message. Compilation time is not included in the performance score.

## 9. Static Analysis Results

Store raw analysis results separately.

Each result may contain:

- comparison_id
- code variant
- tool name
- tool version
- rule
- category
- severity
- message
- source location
- raw result

### Tools by Language

| Language | Security Tool | Code Quality Tool | Complexity Tool |
|----------|--------------|-------------------|-----------------|
| Python | Bandit | Ruff | radon / AST |
| Java | SpotBugs | PMD | Lightweight parser |
| C++ | cppcheck | cppcheck | Lightweight regex parser |
| JavaScript | eslint (security plugins) | eslint | Lightweight parser |

## 10. Complexity Data

Store raw complexity measurements such as:

- Cyclomatic complexity
- Nesting depth
- Function length
- Coupling
- Other approved complexity measurements

Raw measurements must not be replaced by final scores.

These measurements are extracted by language-appropriate parsers.

## 11. Security Findings

Security findings are stored independently.

Each finding may contain:

- comparison_id
- code variant
- tool
- tool version
- severity
- rule
- category
- message
- location

## 12. Scores

Scores should retain:

- comparison_id
- code variant
- dimension
- raw value
- normalized value
- weighted value
- dimension score
- overall score
- scoring configuration version
- normalization population min
- normalization population max
- normalization population n

## 13. Comparison Results

The system should calculate and store:

- AI value
- Human value
- Difference
- Direction
- Percentage difference where applicable
- Statistical status where applicable

Subjective statements should not be stored as research measurements.

## 14. Dashboard Aggregation

Dashboard values should be calculated from stored research records.

The system should support:

- Total problems
- Completed problems
- Remaining problems
- Completion percentage
- Total comparisons
- AI systems used
- Languages used
- AI better outcomes
- Human better outcomes
- Comparable outcomes
- Metric averages
- Metric differences

## 15. AI Usage

The database must allow the system to determine how many comparisons were performed using each AI system and each language.

Example:

ChatGPT → 15 comparisons
Python → 8 comparisons
Java → 4 comparisons
C++ → 2 comparisons
JavaScript → 1 comparison

## 16. Timestamps

Each comparison must contain:

- created_at
- completed_at

## 17. Data Integrity

The database must enforce:

- valid problem references
- valid language values (python, java, cpp, javascript)
- required source code
- valid comparison status
- valid metric values
- valid relationships between comparisons and results

Incomplete evaluations must not be marked as completed.

## 18. Research Data Export

The system must support exporting the collected research data.

The exported data should be suitable for:

- statistical analysis
- spreadsheet analysis
- Python/R analysis
- dissertation tables
- research paper preparation

Exports include language as a column/field to support language-stratified analysis.

## 19. Test Data

Test fixtures may be used during software development.

Test data must be clearly separated from real research data.

The production research dataset must never contain fabricated research results.
