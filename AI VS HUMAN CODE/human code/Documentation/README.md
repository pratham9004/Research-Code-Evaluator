# Research Code Evaluator — Solution Set (200 Solutions, 4 Languages)

## Project purpose
A benchmark solution set of 50 problems × 4 languages (Python, Java, C++,
JavaScript = 200 solutions), built for an MCA dissertation's empirical
evaluation platform comparing code from different sources on correctness,
performance, security, and maintainability.

## IMPORTANT — read before using this in the dissertation
**Every solution in this set was written by Claude (an AI assistant), not by a
human.** Opening a reference link and cross-checking a concept against it does
not make code "human-written" — it is still AI-generated / AI-adapted code.

If the dissertation methodology compares "AI-generated" vs "human-written"
code, this solution set **must not** be labeled as the human-written arm.
Doing so would misrepresent the study's data and could constitute research
misconduct if discovered during review. Recommended framing: treat this as a
third, explicitly-labeled category — **"AI-assisted reference baseline"** —
distinct from both the AI-model-generated submissions under study and any
genuinely human-authored code obtained from real people.

## How to use the solution files
One file per language, 50 functions each, ordered P001→P050, each preceded by
a `// P0xx: Title` (or `# P0xx: Title`) comment. Every function matches the
exact name/signature required by the project's execution harness, per
`FINAL_AI_CODE_GENERATION_SPECIFICATION.md`. No `main()`/`input()`/console
output — the harness is expected to call the functions directly.
- Java: single public class `Solution` with static methods.
- C++: free functions, `#include`s only what's needed, no `using namespace`
  pollution beyond the file itself.
- JavaScript: CommonJS, `module.exports` at the bottom.

## Reference usage methodology
Every one of the 200 reference URLs in the provided Excel index was fetched
directly (GitHub `blob` URLs converted to `raw.githubusercontent.com` and
checked for a real HTTP 200/404). Only links that were both reachable and
topically relevant — confirmed by actually reading their content, not just
their filename — were used as conceptual cross-checks; that was true for 18
of the 200 rows. Everything else is marked "Not Used" with the real reason
(dead link, or a generic/reused library file with no topical connection to
the problem it was listed against). Full detail, including a Summary tab
with the accessible/used counts per language, is in
`References/reference_report.xlsx`.

## Source attribution policy
No source code was copied verbatim from any reference at any point. Where a
reference was genuinely used, only the general algorithmic approach or
concept was cross-checked; every implementation was written independently to
match the benchmark's exact signature and constraints.

## Validation methodology
See `Validation/validation_report.md`. Summary: 200/200 functions present
with correct signatures across all four languages; Python passes `ast`
parsing, Java compiles with `javac`, C++ compiles cleanly with
`g++ -std=c++17 -Wall -Wextra`, and JavaScript passes `node --check`. A total
of 333 self-authored sanity checks were run across the four languages (71 +
87 + 87 + 88) — all passed. These are not the project's own hidden benchmark
test cases, since none were supplied with the uploaded files.

## Known limitations
- Self-authored sanity tests, not an official benchmark test suite — none
  was provided in the uploaded project files.
- Of the 200 reference links in the source index, 182 were either dead or
  not topically relevant to the problem listed against them at verification
  time; this is disclosed row-by-row rather than papered over.
- Not yet run against the evaluation platform's own execution harness or
  hidden test data.
