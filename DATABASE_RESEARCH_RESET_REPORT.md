## 2. Schema and deletion order

Inspected all 12 application tables and their declared foreign keys. `problems` is the benchmark parent. `test_cases` references `problems`. `comparisons` references `problems`; its research child tables reference `comparisons`. `test_case_results` references both `comparisons` and `test_cases`. The schema has no separate submission, saved report, export, or dashboard-cache table. AI/Human source submissions are stored in `comparisons`; dashboard values are derived from database queries.

Foreign-key enforcement was enabled on the reset connection. Child rows were deleted first, then the comparison row. `problems` and `test_cases` were never deleted, updated, reseeded, or recreated.

### Application limitations discovered

The dashboard API still creates 50 display rows with `MISSING` and zero counters when no comparison exists. These are synthesized placeholders, not stored execution results. The request says not to change frontend/backend logic, so I left that behavior unchanged. The UI can therefore still display `MISSING`/`0/0` placeholders even though the database has no old results.

Also, `backend/main.py` imports `python_chatgpt_human_p001_p050_execution_results.json` on application startup whenever the comparisons table is empty. That raw JSON file was preserved as requested. I did not start the app lifespan during verification because doing so would repopulate the database with the old dataset. A subsequent full app restart may reimport it. Keeping both the JSON evidence at its current path and restart-persistent emptiness requires a follow-up startup/import change or an explicitly approved archival move; neither was made in this database-only step.

The dashboard and comparison handlers were queried directly against the cleared active database without running app startup or benchmark code. The `/reports` UI was not browser-automated; its backing comparison-list data is empty.

No partial deletion from the failed attempt was committed.
