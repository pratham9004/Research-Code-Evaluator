## 1. PROJECT OVERVIEW

The Research Code Evaluator is a **research instrument** for empirical comparison of AI-generated code versus human-written code. It does **not** generate AI code, call AI APIs, or require AI keys.

### Core Workflow
```
Dashboard → Solve Problems → Select problem → Select language
→ See function skeleton (auto-loaded) → Paste AI solution function + Human solution function
→ Submit & Compare (Research Data) → Preflight validate → Execute both via typed harness
→ Static analysis → Score six dimensions → Compare AI vs Human
→ Persist all data → Update Dashboard → View Reports → Export Excel/PDF
→ Manage Data (delete old test data safely when needed)
```

### Supported Languages (all 10 problems)
| Language | Runtime | New Execution Contract (Typed) |
|----------|---------|-------------------------------|
| Python | Python 3.11 | Typed function e.g. `def two_sum(nums: list[int], target: int) -> list[int]:` |
| Java | JDK 17 | Typed static method e.g. `public static int[] twoSum(int[] nums, int target)` inside `public class Solution` |
| C++ | g++ 16.1.0 (MSYS2 ucrt64) | Typed function e.g. `vector<int> twoSum(vector<int>& nums, int target)` in plain `.cpp` file |
| JavaScript | Node.js v24.12.0 | Typed function e.g. `function twoSum(nums, target)` + `module.exports = { twoSum }` |

### NEW: FIX 45 — C++ Harness Empty-Value Fallback Bug
`backend/engine/harness.py` `CPP_TYPED_HARNESS`:
For P005–P010, `getField(inp, "key")` correctly returns `""` when the JSON value is
an empty string (e.g. `{"text":""}` → value is `""`). But the fallback
`if(field.empty()) field = inp` then replaced the valid empty string with the full JSON,
causing e.g. `wordFrequency({"text":""})` → `[["text",1]]` instead of `[]`.
Fixed: `if(t.empty() && inp.find("\"text\"") == string::npos) t = inp`
(only fall back if the key literally does not exist in the JSON, not when value is empty).
Same fix applied to P005 (s), P006 (line), P007 (log), P008 (s), P009 (date), P010 (text).

## 7. EXECUTION CONTRACTS — TYPED MODEL (P001–P010)

In the typed model, the user writes ONLY the solution function.
The harness handles: JSON input parsing → typed function call → output serialisation → comparison.

| Language | User writes | Harness does |
|----------|-------------|--------------|
| Python | `def two_sum(nums, target):` | `importlib` load → `_dispatch()` parses JSON → calls `fn(*args)` → serialises result |
| Java | `public static int[] twoSum(int[] nums, int target)` in `public class Solution` | Compiles + runs Runner.java → switch dispatch → reflection invocation |
| C++ | `vector<int> twoSum(vector<int>& nums, int target)` (no main) | Compiles with `-DP001` flag → `#if defined(P001)` branch → native call |
| JavaScript | `function twoSum(nums, target)` + `module.exports = { twoSum }` | `require('./solution.js')` → switch dispatch → native JS call |

### Legacy Contracts (for any future string-in/out problems)
| Language | Contract |
|----------|----------|
| Python | `def solve(data: str) -> str:` |
| Java | `public static String solve(String data)` in `public class Solution` |
| C++ | `string solve(const string& data)` |
| JavaScript | `function solve(data)` + `module.exports = { solve }` |

## 9. SCORING METHODOLOGY (unchanged)

**Overall Score = Σ (Normalized × Weight)**

| Dimension | Weight | Direction | Raw Field |
|-----------|--------|-----------|-----------|
| Reliability | 0.20 | higher_is_better | pass_rate (0–100) |
| Performance | 0.15 | lower_is_better | execution_time_ms |
| Maintainability | 0.20 | higher_is_better | maintainability_index (0–100) |
| Security | 0.15 | lower_is_better | security_findings_count |
| Complexity | 0.15 | lower_is_better | avg_cyclomatic_complexity |
| Code Quality | 0.15 | lower_is_better | quality_findings_count |

Normalization: dataset min/max. Neutral = 50 when max == min.
Population snapshot (`min`, `max`, `n`) persisted per score row.
Note: With only 1–2 comparisons in dataset, scores will be low (first comparison gets neutral 50 on most dims). Scores become more meaningful and spread as dataset grows toward 20–50 comparisons.

## 16. KNOWN LIMITATIONS

1. **Windows AppControl (WinError 4551):** When many C++ compilations run in rapid
   succession in the same Python process, Windows AppControl may intermittently block
   freshly compiled executables. The production API is NOT affected — only rapid-fire
   test runners. Workaround: run C++ validations as separate subprocess calls with pauses.
2. **Score magnitudes are low early in research:** With 1–5 comparisons, overall scores
   like 25 or 40 are normal and expected (dataset normalisation needs range). Scores
   become more representative after 20+ comparisons.
3. **tests/test_api.py uses old B-series IDs:** Will fail against new benchmark. Needs
   rewriting for P-series. Not critical for production use.
4. **validate_languages.py references B013:** Old benchmark reference. Needs updating.
5. **JavaScript timing:** Node.js startup overhead (~50ms) included in first test case.
   Consistent across AI/Human so comparison remains valid.
6. **Java P007 log split:** Uses `"\\n"` literal split — works correctly for Unix newlines.
7. **AI name:** Free-text, case-sensitive in dashboard grouping.
8. **Server reload:** DO NOT use `--reload`.
